### Part 2 — Multi-distro: alpine + debian (trixie/testing) + any ubuntu version, drop-in

- **2a. Two family Dockerfiles, both parameterized.**
  - `docker/Dockerfile.base.alpine` — `ARG BASE_IMAGE=docker.io/alpine:3.21`, apk installs (gcc, musl-dev, make, pv, curl, netcat-openbsd, bash, perl, coreutils, git), `adduser katzenpost`, curl-install of Go at `ARG GO_VERSION` (required build-arg, supplied by the Makefile from go.mod — see 2g).
  - `docker/Dockerfile.base.apt` — `FROM ${BASE_IMAGE}` (covers **debian-trixie, debian-testing, and every ubuntu version**), apt-get installs (build-essential/gcc, make, pv, curl, netcat-openbsd, bash, perl, coreutils, git, adduser), same `adduser` + identical curl-Go lines.
  - Only divergence between families is the package-manager line; **zero per-version code** — versions differ only in the `FROM` tag. Same GO_VERSION recipe in both (this drift is why the old debian path rotted).
- **2b. Generalize base-image rules in make.** Replace `alpine_base.stamp` / `debian_base.stamp` / `debian_base_image?` (lines 529–551) with one adaptive rule `$(distro)_base.stamp: $(base_dockerfile)` running `docker build -f $(base_dockerfile) --build-arg BASE_IMAGE=$(base_image)`. Derivation (uniform, no per-version code):
  - `distro_family = $(firstword $(subst -, ,$(distro)))` (alpine | debian | ubuntu)
  - `distro_version = $(patsubst $(distro_family)-%,%,$(distro))`
  - `base_image`: `alpine` → `alpine_base_image?=docker.io/alpine:3.21`; `debian-<tag>` → `docker.io/debian:<tag>`; `ubuntu-<tag>` → `docker.io/ubuntu:<tag>`; `base_image?=` universal override.
  - Drop-in: `make distro=debian-trixie start wait`, `distro=debian-testing …`, `distro=ubuntu-25.10 …`, `distro=ubuntu-26.04 …` (and `26.10` when released) — no new code.
  - Delete the `docker commit` recipe (lines 531–535) and `debian_base_image?`.
- **2c. `sh` grep (line 97) → `sh?=bash`** (alpine base already installs bash; debian/ubuntu ship it). Removes the last distro-conditional in make.
- **2d. `DISTROS` (line 96) = `alpine debian-trixie ubuntu-26.04`** — the supported set. `make clean`/`clean-images` scrubs every distro ever built, discovered from on-disk stamps/caches (see 6d), so dropping a version later never leaks artifacts. **`test-distros`** brings up, pings, and tears down the testnet on each entry — serially by default, in parallel with `make -j` (see 6b).
- **2e. Minor**: `check-go-version` (line 689) → `katzenpost-$(distro)_base`.
- **2f. Cache scoping (implemented)**: the go module cache (read-only source content) is shared across distros at `cache/go`, but the go **build** cache is per-distro at `cache/go-build-$(distro)` — compiled archives are sensitive to the C library (musl vs glibc, and glibc versions), which Go's cache key does not capture.
- **2g. `GO_VERSION` single source of truth**: `GO_VERSION?=$(shell grep '^go ' ../go.mod | cut -d' ' -f2)` and the base-image rule passes it as a build-arg. The base Dockerfiles declare `ARG GO_VERSION` with **no default**, so a standalone `podman build` fails fast instead of silently pinning a stale Go (the version lives only in go.mod).

### Part 6 — Parallel build/test loop + exit-code-reliable run-ping

- **6a. `-j` binaries**: the per-binary rules are independent in-container build jobs sharing only concurrency-safe caches, so `make -j N testnet_binaries` is safe with no structural change (each rule already recurses via `$(MAKE)`, keeping the jobserver).
- **6b. `test-distros` parallelizable**: a phony `test-distro-<distro>` pattern target per distro; `test-distros` is their union, so it runs serially bare and in parallel under `make -j`. Each leg runs `$(MAKE) -j1 distro=$* base_port=$(lookup) start wait run-ping` and deliberately leaves its `mixnet-<distro>` network running; `net_name` defaults to `mixnet-$(distro)`, so no explicit override is passed. The `-j1` forces the leg's sub-make to keep start→wait→run-ping ordered even when the parent passes a jobserver. `DISTRO_PORTS` derives each distro's `base_port` band (30000 + index-in-DISTROS × 10000) at parse time, so adding/removing a distro reflows the bands automatically. Tear everything down with `make clean` (or `make stop-all`, or one `make distro=<d> stop` per network).
- **6c. `run-ping` exit code**: `cmd/ping` now exits non-zero unless 100% of pings are answered — `sendPings` returns the failed count and the cobra `RunE` returns an error, which the shared fang wrapper turns into exit 1. `run-ping` also dials `/$(net_name)/client/thinclient.toml` instead of the `voting_mixnet`-pinned `client/testdata` symlink (now repointed to `mixnet-alpine`), so it works on any `net_name`; this is what makes each test-distros leg's exit code a meaningful gate.
- **6d. `clean` by discovery**: `KNOWN_DISTROS` = DISTROS ∪ (distros found in `*_{base,go_mod,rust}.stamp` and `cache/{go-build,cargo-home,cargo-target}-*`). `clean-images` loops `KNOWN_DISTROS` and removes both `_base` and `_rust` image/stamp (the `_rust` cleanup was previously dropped), then sweeps orphan containers left by an interrupted `make -j test-distros`. `clean` is `stop-all` (one `stop` per `STAMP_DISTROS`) followed sequentially by `clean-local` (current `net_name` only), `clean-testnets` (git-cleans every `mixnet-<stamp-distro>`), a legacy `git clean -fdx voting_mixnet`, `clean-images`, and the cache wipe. `clean-local` touches only the current network and depends on `stop` (not `clean-bin`, whose binary `rm` is redundant with the git clean).
- **6e. DISTROS trimmed to `alpine debian-trixie ubuntu-26.04`**; artifacts of dropped versions are still scrubbed by 6d discovery.

### Part 7 — `wait` gates on echo-service readiness (single-ping probe)

- **7a. Problem**: on a freshly booted network, `run-ping` immediately after `wait` flakes (~2/3 of legs: 3/10 pings time out then the network warms up within ~2–3 min). The failure is **not** consensus: echo is already advertised in the PKI doc when the flake happens (the ping tool panics if `GetService` fails, and it gets past that). It is per-node epoch convergence — each mix/servicenode/gateway must independently fetch the current consensus, install its per-epoch mix keys, and get its peer links re-authorized (`canSend`), and they converge at their own pace after boot. During the window a straggler mix drops packets as `incoming_out_of_epoch` (incoming_conn.go:388-395) or `outgoing_peer_not_connected` (outgoing_conn.go:460-469); the gate is `AuthenticateConnection` (pki.go:736) which requires the sender to appear in the receiver's *current-epoch* document (early-send slack `Period/8` only tolerates near-transition skew).
- **7b. Verification (done, hypothesis refuted)**: two fresh-boot iterations; scraped `katzenpost_dropped_reason_total` + `katzenpost_dropped_packets_total` per node from the bridge (every node always exports `/metrics` at its `MetricsAddress` — genconfig writes it unconditionally, `no_metrics` only gates the prometheus/grafana compose services, so no config change was needed). Both iterations flaked identically (3/10 pings, exit 2), and **all drops were at the gateway, none at the mixes/servicenodes** (zero `katzenpost_dropped_packets_total` on mix1-3 / servicenode1-3). Gateway reasons: `unwrap_failed` ×5 (2+3) — gateway log shows `sphinx: invalid packet, MAC mismatch` unwrapping the client's outbound packet — plus 1× `outgoing_send_deadline_blown` (egress deadline, iteration 1 only). Root cause: the gateway's per-epoch key installation for client-packet unwrap lags the client's view of the current epoch; the gateway's PKI polling fails at boot (`consensus error code` / `requested epoch has no document`) while dirauths+gateway converge, so it unwraps with the previous epoch's keys. `wait`'s `fetch -r 2` confirms the *client* has the doc, not that the *gateway* (also client-side) has converged. The mix-side `incoming_out_of_epoch` theory from the code-reading was wrong. Design consequence: the failure is exactly on the client→echo round-trip path (first hop: gateway unwrap), so the 7c end-to-end probe remains the right gate — no per-node metric/log predicts gateway unwrap-key readiness.
- **7c. Root cause (confirmed, follow-up investigation)**: mix keys are generated fresh per boot and **never persisted** — `mixkey.New` calls `GenerateKeyPair()` unconditionally (server/internal/mixkey/mixkey.go:174); the bolt file in DataDir holds only the replay-bloom filter, not the key. Meanwhile every container bind-mounts `./:/mixnet-alpine` (docker-compose.yml:13), so the dirauths' consensus + descriptor state survives `compose down` on the host, and `make stop` = `compose down --remove-orphans` **without `-v`** (docker/Makefile:416). A mid-epoch restart therefore leaves the retained consensus pinning the *dead* instances' public keys while the new instances hold fresh random private keys → the client's outbound packet fails the first-hop MAC check at the gateway (`sphinx: invalid packet, MAC mismatch` → `unwrap_failed`). Recovery happens one epoch later, when the new instances' descriptors are voted into a fresh consensus. Evidence: every observed MAC failure followed a down/up with no state clear; iter1 even had an unexpected whole-network restart at 09:45:40 (not user-initiated) and flaked identically; iter2 (`make stop` → `make start`, still not state-clear from the dirauths' view) flaked the same way — gateway restarts 09:51:13, pings 09:51:43/09:52:38/09:53:33 fail, pass from 09:54:27 (epoch 2415897 consensus built from the current instances). Secondary contributor: a late-booting dirauth skips a voting round → a dead epoch with no document (2415892, 2415896), during which no node can be current. Replicas and couriers are **not** affected: replicas already persist their (weekly) per-epoch envelope keys + identity/link keys and reload them at boot (replica/keys.go:44), and couriers hold no per-epoch keys. The fix ships as two independent commits so each is cherry-pickable: **A** (mix key persistence) and **B** (readiness-gated wait).
- **7d. Design — A: persist mix keys on clean shutdown.** New config `[Server] PersistMixKeysOnShutdown` (default false; genconfig emits true for every testnet node). When enabled, the live mix keypairs for the current epoch window are written to `DataDir/mixkeys/mixkey-<epoch>.bin` on clean shutdown (`server.Shutdown` → `mixkeys.Halt`, server.go:215) and loaded on next boot (`mixkeys.Generate` tries `mixkey.Load` first, falling back to generate). A crash never reaches Halt → keys regenerate → the one-epoch outage remains (accepted tradeoff); a clean restart (e.g. an upgrade) reloads the same keys → no divergence, no epoch of packet loss. Keys are stored per epoch, raw private-key bytes for the active scheme; corrupt or scheme-mismatched files fall back to generate-and-log. Known limitations (documented): downtime longer than the persisted window (~3 epochs) regenerates keys; the in-memory replay-bloom state still resets per boot (irrelevant for testnet/CI). The commit implementing this must not touch PLAN.md.
- **7e. Design — B: readiness-gated `make wait`.** Honest per-node readiness = "the current consensus's descriptor for this node matches this node's live per-epoch public key", exported as gauges on each binary's existing `/metrics` endpoint (every node type already serves one on the bridge net): server binary `katzenpost_node_ready` + `katzenpost_node_current_epoch` (1 iff `doc.GetNodeByKeyHash(own).MixKeys[epoch]` byte-equals the local key, set in server/internal/pki's doc-cache path; 0 on the "no document cached for current epoch" path so a restart is never reported ready); replica binary `katzenpost_replica_ready` + `katzenpost_replica_current_epoch` (weekly replica epoch; 1 iff the replica's own ReplicaDescriptor is in the current doc with a matching `EnvelopeKeys[ReplicaNow()]`, set in replica/pkiworker); courier plugin `katzenpost_courier_ready` + `katzenpost_courier_current_epoch` (1 iff the courier PKIWorker has a current-epoch doc cached, courier/server/pki.go:98). `wait` runs `fetch --require-ready` on the bridge network (thinclient-bridge.toml, the pattern run-parallel-load already uses): it discovers every node's MetricsAddress from the net layout (katzenpost.toml `[Server]`, replica.toml, and the courier plugin config path declared in servicenode katzenpost.toml), requires each node ready for its expected epoch (mixnet epoch for server+courier, weekly ReplicaNow for replicas), retries until all are ready or `--ready-timeout` (default 8m) elapses, then prints per-node diagnostics (node, address, ready gauge, epoch gauge vs expected) and exits 1. So `make wait` blocks until the whole testnet — gateway, mixes, servicenodes, couriers, replicas — has caught up, and succeeds only when every node's keys match the current consensus. Caveats to document: necessary-not-sufficient (a node can be ready yet a specific route still fail), and kpclientd's thinclient needs a few seconds after the gateway is ready.
- **7f. Verify the fix + docs**: `make stop && make start && make wait && make run-ping` → pings pass; mid-epoch restart with A → persisted key files appear under DataDir/mixkeys/ and `make wait` succeeds without a dead epoch; `kill -9` a mix → fresh keys on boot (A correctly does not paper over crashes); each commit builds and tests alone (cherry-pickable). Update the `wait` help text and `docker/README.rst` `wait` description to reflect full-testnet readiness gating.
